# Скилл для агента

Эта страница показывает, как выглядит минимальный скилл, который умеет работать с Anchor без лишней болтовни.

Идея простая: агент не должен помнить весь продуктовый контекст в голове. Он должен знать последовательность:

1. проверить здоровье системы;
2. загрузить конфиг;
3. работать через `notes`, `tasks`, `history`, `files`, `search`;
4. держать ответы компактными;
5. расширять контекст только когда это реально нужно.

## Когда такой скилл нужен

- если новый человек подключает собственного агента к Anchor;
- если нужен единый стандарт работы для нескольких агентов;
- если хочется убрать разрозненные “памятки” и оставить один контракт;
- если важно, чтобы агент не начинал сразу тащить полный контекст.

## Что скилл должен говорить агенту

```md
# Скилл Anchor для агента

Ты работаешь с локальным SQLite-контуром Anchor.

Правила:
- сначала вызывай `anchor health`;
- если есть сомнения в настройках, вызывай `anchor config get`;
- для навигации используй `list`;
- для одной сущности используй `get`;
- для поиска используй `search`;
- держи `--project` явным;
- по умолчанию проси компактный ответ;
- полный ответ включай только когда он действительно нужен;
- cross-project search включай явно через `--projects`;
- не тащи полный объект, если достаточно короткой карточки;
- не дублируй один и тот же контекст в нескольких сущностях.

Рабочий порядок:
1. Сначала `search` или `list`.
2. Если данных не хватило, делай `capture` / `add` / `append`.
3. Если нужно обновить состояние, используй `update`.
4. Если нужен след работы, фиксируй его в `history`.
5. Если работаешь с репозиторием, индексируй `files` и используй `files search`.

Если retrieval уже дал достаточно контекста, не расширяй его без причины.
```

## Более практичный вариант

Если нужен не просто текст, а рабочий файл с минимальными правилами для агента, можно оформить скилл так:

```md
# Триггер
- когда агент должен работать с Anchor как с локальной памятью и retrieval-слоем

# Рабочий процесс
1. `health`
2. `config get`
3. `list` / `search`
4. `add` / `update` / `delete` при необходимости
5. compact-ответ по умолчанию

# Результат
- машинно-читаемый JSON
- сначала короткий результат
- полный результат только по явному запросу

# Критерии готовности
- агент знает порядок действий
- агент не тянет лишний контекст
- агент использует project scope явно
```

## Что важно не забыть

- скилл должен быть коротким;
- в нём должна быть явная последовательность действий;
- он должен уменьшать token burn, а не просто описывать продукт;
- он должен быть одинаково понятен и человеку, и агенту.

## Рекомендуемый минимум

Если делать совсем коротко, то достаточно трёх правил:

- `health` перед работой;
- `search/list` перед `add/update`;
- `compact by default`, `full only when needed`.
