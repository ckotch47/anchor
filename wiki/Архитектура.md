# Архитектура

Anchor — это модульный монолит.

## Как он устроен

- `main` только собирает приложение
- `application/system` отвечает за конфиг, здоровье, миграции и maintenance
- `application/<domain>` хранит use-cases
- `application/links` хранит typed links
- `adapters` общаются с SQLite и внешними системами
- CLI — основной транспорт
- MCP по `stdio` — опциональный тонкий транспорт поверх того же ядра

## Базовые принципы

- один SQLite-контур как source of truth
- один локальный инстанс на пользователя
- без обязательного сервера
- retrieval-ready с самого начала
- компактные ответы по умолчанию
- correlation id как общий след действий
- typed metadata schema и typed links как часть доменной структуры

## Основные контексты

- `notes`
- `tasks`
- `history`
- `files`
- `search`
- `config`
- `ops`
- `memory`
- `links`

## Данные

- `documents` — общий позвоночник для текстовых сущностей
- в `documents` живут `correlation_id`, `project`, `title`, `body` и общий lifecycle
- доменные таблицы хранят состояние конкретного типа
- derived tables хранят retrieval state, embeddings и индексы
- файловая индексация хранит метаданные и retrieval slices, а не копию репозитория

## Retrieval pipeline

1. lexical candidates
2. vector candidates
3. rerank
4. dedup
5. trim to budget
6. compact response

## Операционка

- `health` может запускать плановое обслуживание
- `db compact` — явный путь на чистку
- WAL, tombstones и FTS fragmentation считаются нормальной частью обслуживания
- maintenance должен быть best effort и не ломать обычные операции

## Что не делаем

- микросервисы
- multi-user backend
- self-HTTP между модулями
- отдельную БД под каждую фичу
